HOME WALLET — ACTIVE PROCESS REFERENCE

SCOPE
This file documents wallet process logic and functional requirements only.
Do not include personal names, real or sample amounts, example financial data, account identifiers, external platform configuration, retired requirements or design mockups.
Consult application source files for current UI design and implementation.
Keep README.md empty.

GROUPS
Income (stored as IN for legacy compatibility): recurring or manually entered spendable income items.
Saving: protected and accessible savings items.
Bills: recurring, variable and periodic obligations.
Others: custom payees or purchases, organised by item rather than subfolders.
Custom categories: user-created expense groups, stored using their category label and counted as planned expenses.
Withdraw: a savings action in the Add form, not an ordinary charge group.

INCOME
- Support repeating default values until manually changed.
- Support irregular income entered only when confirmed.
- Store month-specific amounts, including explicit zero when nothing arrives.
- Combine applicable income for the selected planning month.
- No cumulative balance tracking for individual income items.

SAVING
- Transfer planned allocations from IN into savings during monthly payment processing.
- Allocations are deducted from spendable income, and credited once to the relevant savings balance.
- Protected savings permit allocations and balance tracking but NEVER withdrawals or bill funding.
- All savings default to protected; the user must explicitly mark an existing savings item as accessible in Savings settings.
- Withdraw appears in the category selector and shows a themed "Are you sure?" popup immediately upon selection.
- Only accessible savings with verified confirmed balance may be withdrawn. Refuse zero, overdrafts, stale balances, and protected savings.
- Until the payment workflow can confirm current-month allocations, exclude the current month's savings additions from the amount available to withdraw.
- Confirmed withdrawals append a revised Savings TXT balance snapshot for the current month and never erase earlier lines.
- Accessible savings permit explicit withdrawals only from already confirmed saved funds.
- Future or uncommitted allocations must not be made available for withdrawals.
- Carry the last confirmed savings balance into the next month.
- Balance = last confirmed balance + committed savings additions - confirmed withdrawals.
- Savings settings allow a private monthly target amount per existing savings item. Default target is zero until chosen.
- A known opening savings balance can be stored as a private metadata value, separate from both saved deposits and planned monthly allocations.
- An unknown savings opening balance remains unknown (display an em dash), never silently invent zero.
- On each month view, calculate IN minus all Bills, Others and custom expense groups, and minus existing current-month recorded savings additions.
- Automatically reduce ONLY uncommitted savings targets to fit the income remaining after those obligations, never below zero.
- Distribute an affordable monthly savings budget proportionally across eligible savings targets, using exact cents and stable remainder allocation.
- If a savings item has a current-month ledger snapshot, treat its saved addition as already committed and do not create a second plan allocation for that item.
- Show the saved balance unchanged, with a separate Save or Adjusted planned contribution beneath it. The monthly Balance includes the adjusted plan.
- This adjustment is a forecast only: do not write a reduced saving into payment history, alter existing paid records, change purchases in Others or perform a withdrawal.
- If income cannot cover non-savings spending or already committed savings, show the actual deficit: reducing planned savings cannot eliminate that shortfall.
- Recalculate individually for each month when records or targets change; do not overwrite other months.
- Savings balances remain separate from ordinary spendable income.

BILLS
- Only Bills supports an opt-in Recurring monthly control in Add and Update.
- An authenticated one-time import may configure private recurrence schedules for Income, Bills and Others independently of the Bills form checkbox.
- A Bills recurrence rule is stored in the same private per-item TXT file as an append-only metadata directive; non-Bills groups are never generated automatically.
- Initially fill selected current or future months through December 2027, without editing locked earlier months.
- From June 2027, on the next authenticated wallet open or refresh, generate missing months for 2028 and 2029. From June 2029 generate 2030 and 2031, continuing every two years.
- A renewal is performed only while the authenticated wallet is open, not by a background server.
- Generate one unpaid monthly snapshot per missing month using the saved recurring template; never overwrite an existing month, edited record or DELETE marker.
- Preserve manual changes, historical lines and already-recorded payments. A deleted month must not return automatically.
- Updating one occurrence changes only that month, unless the Recurring toggle is explicitly switched.
- Switching recurrence off stops later automatic generation; months already saved remain until individually changed.
- Re-read and verify private TXT contents after each recurrence write. A failed generation can be retried after Refresh without duplicating successfully written months.
- Private @SCHEDULE directives support monthly, designated annual months, and fixed service intervals; optional dated amount changes must be explicit.
- No missed recurrence reminders are replayed: only the present reminder date or lead month may trigger a new popup.
- When service history contains a newly fully paid service, derive the next reminder from that actual latest paid-service month.
- Recurring charges may be fixed, calendar-calculated, variable or contract-dependent.
- Periodic charges appear only in configured due months, with reminders.
- Others accepts new individual items, optional shop information, URL and remarks.
- Multiple charges against an existing Others item accumulate under that same item.
- Paid and unpaid portions are tracked; bills do not need ongoing account balances.
- Any unpaid remainder carries to the following month under its original item/category.
- If an existing group/item cannot be matched, place the carried item under Others.
- Never count a carried amount twice or duplicate it when a new monthly charge is added.

SALARY / MONTHLY FORECAST
- Salary is normally received on the last working day of the month.
- The salary received in an active month supports settlement for that month and spending until the following salary.
- Store period identifiers as YYYYMM.
- Set A = total spendable IN entries applicable to the active month.
- Set B = savings allocations + current Bills + Others + outstanding carry-forward, counted once.
- Forecast = Set A minus Set B.
- The implemented Balance uses the latest saved entries: IN minus Bills, Others, custom expenses, committed savings additions and the affordable portion of monthly savings targets.
- Never report an artificial zero balance when obligations already exceed income.
- Carried savings balances are never counted as spendable income or deducted again in later months.
- Automatic unpaid carry-forward is not yet available, so the current Balance does not include unrecorded carried obligations.
- Recalculate the displayed Balance after successful Add, Update, Delete and Refresh, and display it in the primary table's selected currency using the same verified reference rate.
- When records are incomplete or fail to load, do not show a misleading calculated amount.
- Forecast is a planning estimate, NOT actual bank balance.
- Do not require tracking actual bank balances or a post-payment spending balance.
- A change to an open month's entries immediately updates the forecast.
- Warn about insufficient forecast funding.
- Alert on upcoming periodic and Others items.

WALLET ACCESS PROCESS
- A successfully signed-in account is checked against the authorised wallet identity before any wallet or storage controls become available.
- When a different account signs in, display the verified account email, a clear "You are not authorized" message and a Sign out button; do not load wallet data.
- A returning browser may be remembered for convenient faster sign-in, but this is an opt-in preference only, not proof of identity.
- Every new session still requires successful identity verification; never use computer name, IP address, or browser preference as a substitute for authentication.
- Never store passwords, long-lived credentials or access tokens in persistent browser storage.
- A user-opted-in browser may hold a short-lived token in tab-scoped session storage to support safe refreshes; verify the account again before opening records, expire the token and clear it on sign out.
- When an expired session cannot be restored, require an explicit user sign-in and fresh file-access permission.
- Private file permissions remain the ultimate data access boundary.
- A successful authorised sign-in also requests private file-access permission in the same user-initiated flow; the application checks its storage folder automatically.
- Do not require a separate connection button on ordinary successful sign-in.
- When the short-lived permission expires, require renewed user action; do not store a permanent browser token or promise uninterrupted sessions.

MAIN VIEW
- One month-based consolidated table with collapsible groups and item details.
- Display the former IN group as Income while preserving existing IN TXT records.
- Place custom categories beneath the fixed groups and include their entries in expense totals.
- Item-name hover/focus displays private notes in a floating tooltip without exposing them publicly or altering the Remark column.
- Use one rounded, theme-coloured dialog with Cancel and OK for Delete and Withdraw confirmations and service reminders; confirmations use the short wording "Are you sure?".
- Keep the primary monthly table on the current month.
- A separate Other months comparison view navigates earlier and future months independently without changing the primary table.
- The comparison uses the same item data, group contents, details and valid Update actions; historical periods remain read-only.
- New or amended records refresh both views from the same confirmed storage data.
- Monetary amounts are entered, recorded and calculated in MYR; switching the table's display currency must never alter underlying records.
- The primary monthly table and Other months comparison window independently select RM or Korean won; one view's choice never changes the other view.
- Both views may reuse the same verified published exchange-rate lookup without storing converted amounts.
- Korean won display uses the latest available published conversion rate, shows its date and source, and always rounds positive converted amounts upwards to the next whole hundred won.
- Conversion errors or unavailable rates must be clearly indicated; never show fabricated or hard-coded rates or treat estimates as payment values.
- Display income, planned dues, protected/accessible saved balances and alerts.
- Maintain a separate live list of outstanding Others items.
- Work cleanly on mobile and desktop browsers.
- No charts.

ADD / EDIT / REMOVE FORM
- Category is a dropdown with existing groups, Withdraw, and Add new category.
- An authorised wallet Import action accepts a locally selected private setup file, displays a confirmation, and writes only through the signed-in browser's existing Drive connection.
- Do not embed imported names, amounts, dates or notes in public GitHub files or persistent browser storage.
- Run import preflight on every target before any write, preserve existing edited, paid or deleted month snapshots and existing private settings.
- Repeated imports must safely skip already-added items and be restartable after a failed or interrupted upload.
- Name-only items use an @ITEM catalog marker in their private TXT file, with no fabricated amount row, and appear in their category's Item dropdown.
- Item is a dropdown filtered to the selected category, with Add new item for creating another item in that category.
- Custom categories are valid user-named expense groups; do not allow custom names that conflict with reserved categories or commands.
- The same item name may exist in different categories without mixing histories.
- More options allows editing private hover notes and optional service dates/reminder settings; these are separate from user Remarks.
- Savings settings permits an explicit access designation and private hover note but does not edit saved financial balances.
- Date: select the current or a future payment month; allow typed dates converted to YYYYMM.
- Amount: numeric MYR, without a currency prefix in the entry field.
- Retail: shown only for Others.
- Remark: optional text on every group. The monthly Details column shows only the latest user-entered remark for each item, without payment calculations or technical status text.
- Others may also store a URL to the shop or item.
- Submit and Cancel must both be available even when fields are empty.
- Cancel returns to the prior screen, with no save.
- Submit updates the corresponding item log and month table.
- When updating an item, place Delete at the lower left, and Cancel then Update at the lower right.
- Delete applies only to the selected open-month item, never to the entire per-item TXT file or other months.
- Before deleting, ask with the themed "Are you sure?" dialog. Cancellation must not write or change anything.
- A confirmed Delete appends a four-field tombstone: MainCategory, Item, Month, DELETE.
- A valid tombstone becomes the effective state for that item/month and hides it from the current and comparison month tables; earlier snapshots remain in the file.
- Deleting an IN entry removes its contribution from that month's planned income. Deleting an unpaid Bills or Others entry removes its planned obligation for that month.
- Bills/Others entries with any recorded paid amount cannot be deleted; paid history and confirmed savings are never cleared via ordinary Delete.
- Re-adding a deleted item in the same month appends a fresh item snapshot, restoring it without removing the old history.
- Forecasts and outstanding totals, when enabled, use only the latest effective non-deleted item/month state; future-month records are not changed by a deletion.
- Empty groups display a simple No items row instead of looking broken.
- Add may create IN, Bills and Others entries for the current or future months, only after explicit submission; for existing items it may append a new month while preserving historical lines.
- A second Add for the same item/month is refused; use Update to amend the existing month instead.
- Update is available for open-month IN, Bills and Others item rows and appends a new complete snapshot to the same item TXT log without deleting previous lines.
- A stale Update must be refused if the item's current saved snapshot differs from the loaded record.
- Updating a bill or Others item preserves the amount already paid, recalculates the remaining unpaid amount, and refuses a revised charge below the amount paid.
- Protected and accessible savings balances are not directly editable through the ordinary item Update control; their changes belong to the separate savings/payment process.
- Readable amount displays omit trailing zero decimals while preserving nonzero cents and exact values in the TXT logs.
- New Bills and Others obligations start unpaid; actual payment updates are handled separately.
- Saving entry creation is deferred until the payment flow can safely commit allocations and balances.
- For Others, optional retail, URL and remark follow the core payment fields as trailing tab-delimited fields.
- For IN and Bills, an optional remark follows the core fields, leaving the original format unchanged if the remark is empty.
- Existing Saving records may also carry an optional remark after their balance.
- Incomplete submissions must not corrupt calculations; the precise safe representation is pending.
- Amendments append revised log entries; historical lines remain preserved.
- Do not edit completed previous months.

PRIVATE SERVICE REMINDERS
- The user may set a last-service month, a repeat interval and a reminder lead time for relevant items.
- Based on the latest service month, remind after the scheduled advance period when the wallet is opened or refreshed while authenticated.
- If a later recorded service is fully paid, use that month as the updated last-service reference where applicable.
- Service reminders use the same rounded Cancel/OK popup styling as other confirmations.
- Dismissed reminders are suppressed during the active page session, not silently marked as paid.
- No background checks occur while the wallet is closed, and no calendar data is fetched by this feature.

START PAYMENT
- Start Payment loads the active month's planned income, allocations and payable obligations.
- Display bills for full, partial or unpaid selection and review.
- Regular spendable funds are the default payment source.
- Using accessible saved funds is deliberate, never automatic, and is limited to confirmed savings.
- Never offer protected savings as a payment source.
- Extra human-error prevention controls are still to be designed.

END PAYMENT
- End Payment finalises a month once, even if pressed repeatedly or the page reloads.
- Apply confirmed paid/unpaid results and savings contributions exactly once.
- Transfer only unpaid balances into the next month's matching item/category.
- If an item does not match an existing category, group it in Others.
- Combine new Others charges with outstanding amounts without duplication.
- Append all relevant log updates and retain historical records.
- Confirm all storage writes finished successfully BEFORE marking a month completed.
- Failed or partially saved processing must be recoverable and safe to retry.
- On successful completion, close that month and open the next month.
- Completed months are not reopened for corrections.
- A correction affecting a completed payment is recorded as an adjustment to the following month's outstanding obligation.

USE SAVINGS
- Provide a separate accessible-reserve withdrawal action.
- Form: Item, Payment Month, Amount, Remark, Submit.
- Protected savings cannot be selected.
- Allow only the amount already confirmed saved, not a future monthly allocation.
- After a confirmed save, append a withdrawal record and update the savings balance.

RECORDS / STORAGE
- Single private storage folder named Wallet bills.
- One plain UTF-8 .txt file per unique item, containing all applicable months.
- No category subfolders and no separate file for each month.
- Text lines are tab-separated, with YYYYMM month values.
- @ITEM catalog markers and @SCHEDULE recurrence directives are metadata, not payment entries.
- IN fields: MainCategory, Item, Month, Amount.
- Saving fields: MainCategory, Item, Month, Added, Withdrawn, Balance.
- Bills/Other fields: MainCategory, Item, Month, BillAmount, Paid, Unpaid.
- Optional remark fields and Others retail/URL fields are compatible with legacy entries that lack these extras.
- Private item settings are stored as append-only @META JSON directives inside the item's private TXT file; these directives are not money entries.
- A private @META can enable hover display of the live unpaid remainder instead of hard-coding an outdated balance.
- Only the latest valid @META for the same category and item is effective. Never write private notes, reminders, or financial amounts to public GitHub files.
- A Savings @META access setting must be explicitly accessible before a withdrawal; the default is protected.
- Recurring Bills metadata directives begin with @RECUR and are not financial rows; only valid Bills rules affect automatic month creation.
- Append all changes instead of erasing past records.
- The LAST valid row, including a valid DELETE marker, for a specific item/month is the effective state for that month.
- A later version of an existing record is not a second charge.
- Additional charges for an Others item must be represented as a revised cumulative amount or explicitly identified new charge events, not as accidental double-counted snapshots.
- Keep explicit zero-activity month records where needed to identify gaps.
- Keep savings balance history permanently.
- Keep inactive/completed payment history in append-only logs, while hiding completed past months from the active table.
- If an individual item file exceeds the agreed size threshold, continue its history in a second indexed segment; treat all segments as one continuous log.
- Maintain a separate backup/export ability and verify each save.

SHAREABLE OUTSTANDING SUMMARY
- Export the active and following month's unpaid/expected items, due months and totals.
- The summary supports requesting additional household funds.
- Exact export file format is undecided.
